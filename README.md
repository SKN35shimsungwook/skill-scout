# skill-scout

제 Claude Code 대화 기록을 보고, 제가 자주 하는 작업에 맞는 **스킬·플러그인을 매일 아침 디스코드로 추천받으려고** 만들었습니다.

## 왜 만들었나

Claude Code를 매일 쓰는데, 확인해 보니 설치한 플러그인이 0개였습니다. 공식 마켓에만 플러그인이 300개 넘게 있고 skills.sh 같은 곳에도 스킬이 계속 올라오는데, 무엇이 저한테 맞는지 고르기가 어려워서 그냥 안 쓰고 있었습니다. PDF를 그대로 올리다가 마크다운으로 바꾸면 토큰이 덜 든다는 것도 한참 뒤에 알았습니다. 이런 걸 누가 먼저 알려 주면 좋겠다고 생각해서, 최종 프로젝트(AI 사용 환경 관리 비서)의 "도구 맞춤" 기능을 제 기준으로 먼저 만들어 봤습니다.

## 두 가지 사용 방법

| 메뉴 | 기준 | 언제 |
|---|---|---|
| 💬 상담 | 지금 하려는 작업 | 새 작업 전에 "뭐 챙기면 돼?"라고 물으면 상담팀이 받아서 부서들이 준비물(이미 있는 도구 + 설치 추천)을 챙겨 줍니다 |
| 🏢 아침 점검 | 최근 30일 내 사용 이력 | 매일 자동 실행 → 디스코드 브리핑 (08:00, 절전 중이었으면 그날 처음 노트북을 열 때). 사무실 화면에서 지금 실행도 됩니다 |

상담팀만 Gemini 무료 API를 씁니다(질문 이해·답변 문장). 키가 없거나 한도를 넘으면 단어 매칭으로 대신합니다. 나머지 부서는 규칙 기반이라 토큰을 쓰지 않습니다. Gemini에는 상담 질문과 추천 결과만 보냅니다.

화면은 4차 팀 프로젝트(Langration)의 디자인 규칙(밝은 배경, 검정 버튼, 보라 포인트, 사이드바 메뉴)을 따랐습니다.

## 아침 디스코드 브리핑 구성

매일 아침 8시에, 노트북이 절전 중이었으면 그날 처음 열 때 섹션마다 메시지를 따로 보냅니다(하루 한 번). 도구 추천 말고는 모두 PC 안의 기록만 읽고, 토큰을 쓰지 않습니다.

| 순서 | 섹션 | 내용 |
|---|---|---|
| 1 | 📂 어제 작업 브리핑 | 어제 Claude 대화별 마지막 요청, 사용 한도·중단으로 끊긴 작업, 남은 할 일, 고친 폴더의 커밋·push 안 한 변경 → **오늘 이어서 할 것** |
| 1-1 | 📋 할일 지킴이 | `Desktop/todo-keeper`(별도 저장소)가 있으면 붙습니다. 고를 후보, 멈춘 프로젝트(권유 횟수), 진행중, 이번 주 집중, 주간 점검 여부. 고르기는 그날 첫 Claude 대화에서 합니다 (스크립트가 없거나 실패하면 이 섹션만 빠짐) |
| 2 | 🩺 상태 점검 | 메모리에 적힌 마감 D-day(+ `data/deadlines.json`), GitHub Actions 실패, push 안 한 커밋, README에 적힌 배포 앱 응답 |
| 3 | 📊 사용량·습관 팁·업데이트 | 어제 토큰(출력·캐시), 가장 많이 쓴 대화, 습관 팁(긴 대화·PDF 원본 읽기·'간단히' 반복·중단), Claude Code 새 버전 |
| 4 | 🧩 도구 추천 | 아래 부서 흐름 결과 |
| 5 | 📝 지난주 요약 (그 주 첫 전송) | 대화·요청 수, 많이 한 작업, 저장소별 커밋, 못 끝낸 작업, 대화 정리 추천 (주간회고 재료) |

## 어떻게 동작하나

팀 기획서처럼 다섯 부서가 차례로 일을 넘기는 구조로 만들었습니다. 흐름은 LangGraph로 연결했고, 부서마다 규칙 기반이라 LLM 토큰은 쓰지 않습니다.

```
① 수집기 → ② 점검팀 → ③ 검증팀 ─(통과 후보 부족)→ ② 점검팀 재검토
                                 └(충분)→ ④ 브리핑팀 → ⑤ 상담팀
```

| 부서 | 하는 일 |
|---|---|
| ① 수집기 | 제 대화 기록에서 작업 신호를 세고(원문은 PC 밖으로 안 나감), 공식 플러그인 마켓·Anthropic 스킬·skills.sh에서 후보를 모읍니다 |
| ② 점검팀 | 이미 있는 것은 빼고, 제 작업과 겹치는 정도로 순위를 매겨 4개씩 검증팀에 넘깁니다. 흔한 신호는 가중치를 낮췄습니다(IDF) |
| ③ 검증팀 | GitHub 저장소가 있는지, 보관 처리됐는지, 1년 넘게 방치됐는지, 사용자가 너무 적은지 보고 PASS·경고·실패를 판정합니다. 통과가 모자라면 점검팀에 다음 후보를 요청합니다 |
| ④ 브리핑팀 | 통과한 후보로 브리핑을 쓰고, 전날과 비교해 새로 나온 것을 따로 표시해 디스코드로 보냅니다 |
| ⑤ 상담팀 | 오늘 무엇부터 써 보면 좋을지 한 줄로 정리합니다. 설치는 제가 직접 승인합니다 |

부서마다 진행 상황을 이벤트로 남기고, 2D 오피스 화면이 그 이벤트를 받아 캐릭터를 움직입니다.

## 아침 브리핑이 안 오던 문제를 고친 과정

처음에는 작업 스케줄러에 08:00 실행을 걸고 "절전 중이면 깨워서 실행"까지 켜 두면 끝이라고 생각했습니다. 그런데 만들고 바로 다음 평일인 11월 9일과 10일 아침에 디스코드가 조용했습니다. 스케줄러 결과와 `data/run.log`, Windows 전원 기록을 시간순으로 맞춰 보니 프로그램 오류가 아니라 노트북의 절전 방식과 제 설정이 맞지 않는 문제였습니다.

| 시각 | 일어난 일 |
|---|---|
| 11/8 12:59 | 노트북이 절전에 들어가 11/10 09:10까지 절전 상태로 있었습니다 (새벽에 몇 초씩 깬 것 제외) |
| 11/9 08:00 | 전원이 연결돼 있었는데도 깨어나지 않아 실행되지 않았습니다 |
| 11/10 03:33 | 잠깐 깬 틈에 놓친 11/9분이 시작됐지만, 곧바로 절전에 들어가 프로세스가 멈췄습니다 |
| 11/10 08:00 | 이날도 깨어나지 않았습니다 |
| 11/10 09:10 | 노트북을 열자 오늘 분을 실행하려 했지만, 03:33 실행이 안 끝난 상태라 동시 실행 금지 설정에 걸려 거부됐습니다 (`0x800710E0`) |
| 11/10 09:13 | 멈췄던 03:33 실행이 다시 돌아 끝나면서 브리핑을 보냈습니다. 화요일에 보내진 셈이라 월요일 전용이던 지난주 요약은 빠졌습니다 |

원인은 세 가지였습니다.

1. 제 노트북은 절전이 모던 스탠바이(S0 저전원 유휴) 방식이고, 이 상태에서는 "깨워서 실행" 설정을 켜 둬도 08:00에 깨어나지 않았습니다.
2. "놓친 작업 나중에 실행"이 켜져 있어서, 새벽에 잠깐 깬 순간 실행이 시작됐다가 절전과 함께 얼어붙었습니다.
3. 지난주 요약이 "월요일에 실행되면 포함"으로 짜여 있어서, 월요일 실행을 놓치면 그 주 요약이 통째로 사라졌습니다.

그래서 "정해진 시각에 PC를 깨운다"는 생각을 버리고, **노트북을 여는 순간을 실행 시점으로** 바꿨습니다. 대신 잠금을 풀 때마다 돌게 되므로 하루 한 번만 보내는 장치를 넣었습니다.

### 지금의 자동 실행 규칙

| 항목 | 동작 |
|---|---|
| 실행 시점 | 08:00, 잠금 해제 1분 뒤, 로그인 1분 뒤 (1분은 Wi-Fi가 붙을 시간) |
| 하루 한 번 | `data/state.json`의 `last_sent_date`가 오늘이면 건너뜁니다. 사무실 화면에서 보낸 것도 오늘 보낸 것으로 칩니다 |
| 새벽 전송 금지 | 06시 전에는 보내지 않습니다. 밤늦게 작업하다 잠금을 풀 때 브리핑이 오는 일을 막습니다 |
| 전송 실패 | 전송이 끝나야 기록하므로, 실패하면 다음 잠금 해제 때 다시 시도합니다 |
| 지난주 요약 | `weekly_sent`에 이번 주 월요일 날짜가 없으면 그 주 첫 전송에 붙입니다. 언제 보내도 범위는 지난주 월~일이고, 커밋 수도 같은 범위로 셉니다 |
| 직접 실행 | `python run.py`와 사무실 화면의 전송은 하루 한 번 제한을 받지 않습니다. 제한은 `--scheduled`를 붙인 자동 실행에만 걸립니다 |

작업 스케줄러 설정은 저장소에 들어가지 않아서 여기에 적어 둡니다.

| 설정 | 값 |
|---|---|
| 작업 이름 | `skill-scout 아침 브리핑` |
| 트리거 | 매일 08:00 / 세션 잠금 해제(지연 1분) / 로그온(지연 1분) |
| 동작 | `conhost.exe --headless cmd.exe /c <저장소 경로>\run_daily.bat` (잠금 해제 때마다 검은 창이 뜨지 않게) |
| 놓친 작업 나중에 실행 | 끔 |
| 여러 인스턴스 | 새 인스턴스 시작 안 함 (`IgnoreNew`) |

실행할 때마다 `data/run.log`에 시작 시각과 결과가 남고, 건너뛰면 `오늘 이미 보내서 건너뜀`처럼 이유가 적힙니다.

이번에 배운 점은 예약 작업이 "제시간에 실행됐다"는 표시만 믿으면 안 된다는 것입니다. 스케줄러는 실행 중으로 나왔고 로그에는 시작 줄이 있었지만, 실제로는 5시간 넘게 멈춰 있었습니다. 노트북에서는 PC가 항상 깨어 있다는 전제를 두지 않고, 사용자가 돌아오는 시점에 맞추는 편이 맞았습니다.

## 실행

```bash
pip install -r requirements.txt
cp .env.example .env        # DISCORD_WEBHOOK_URL 입력
python run.py --dry-run --verbose   # 전송 없이 부서별 진행 상황과 결과 확인
python run.py                       # 지금 바로 디스코드로 전송
python run.py --scheduled           # 자동 실행과 같은 규칙 (오늘 이미 보냈거나 06시 전이면 건너뜀)
python run.py --dry-run --weekly    # 이번 주에 이미 보냈어도 지난주 요약 포함해서 미리 보기
python office.py                    # 상담·사무실 화면 (http://localhost:8565)
```

## 아직 부족한 점

- 단어 매칭 방식이라 가끔 엉뚱한 후보가 섞입니다. 👍/👎 피드백을 받아서 고쳐 나갈 생각입니다.
- ko-skills는 화면을 브라우저에서 그리는 방식이라 아직 목록을 가져오지 못했습니다.
- 노트북이 절전이면 정확히 08:00에는 받지 못하고, 그날 처음 열 때 받습니다.
- 한 주 내내 노트북을 열지 않으면 그 주에는 전송이 없고, 다음 주에는 바로 전 주의 요약만 옵니다.
